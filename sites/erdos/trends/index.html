      How the numbers are counted

      Upstream moved its summary statistics off the README and froze its own progress chart on October 6, 2026. Its problem data remains active. This independent view reads that data and checks the latest counts against the upstream summary on each refresh.

      Each catalog defines which statuses count as resolved. Bloom–Tao counts proved, disproved, and otherwise solved. Plasma includes accepted independence results. Combined uses the union by problem number.

      A statement in Lean expresses the question in a formal language. A solution in Lean records a formal proof or disproof. Neither identifies who or what produced it; human review of the problem’s status can lag formalization.

      Model markers show selected public Claude, OpenAI, and Google Gemini releases (toggle “All” on the pace chart for the full catalog in model-releases.json). Dates provide timeline context; comparing windows does not establish causation.

      Each catalog starts with its first usable snapshot as the baseline. Combined starts at the earliest catalog snapshot and carries forward each catalog’s last observation. When a catalog joins, its opening balance contributes to totals and appears as a baseline in monthly changes. Pace and release comparisons count changes after a catalog’s first snapshot. Lean statement metrics use catalogs that report them.

      The resolved share rose from 35.5% to 48.1%. The database grew by 229 problems; unresolved problems went from 640 to 634.

      352 initially resolved + 188 changes to resolved + 54 added as already resolved − 6 changes back to unresolved − 1 removed from the database = 587 currently resolved. New database entries can describe old results.

      Daily averages count changes to existing problems. Each window starts at the last snapshot on or before its target start date. The count is divided by the actual days elapsed, shown below the chart.

      Monthly bars count changes in the month they first appear. The first and last months may be partial. All categories add up to the net change.

      Release comparisons use the 30 UTC dates before the release date and the 30 dates starting with it. An observed change is definitely inside a window only when its whole snapshot interval fits inside it. Intervals spanning a boundary contribute to a possible upper count, not a definite count. When a window has boundary-spanning intervals, the card displays the bounded rate range rather than inventing an exact rate or multiplier. Bounds cover captured changes, not all mathematical activity or all database edits.

      Gaps include days without updates and revisions skipped for invalid status data. Changes between snapshots may be missed or recorded later. Duplicate problem numbers cannot be matched reliably; their effect appears as “unmatched changes.”
