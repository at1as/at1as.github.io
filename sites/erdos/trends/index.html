What do “resolved” and “Lean” mean?

Resolved includes problems that have been proved, disproved, or otherwise solved. The remaining statuses are grouped as open or unresolved.

Lean is software for checking mathematical proofs. Writing a problem’s statement in Lean is different from checking a solution. A Lean solution may be listed before the database’s resolved status is updated.

Why timing is uncertain

The lower count includes changes whose whole snapshot interval is inside the window. The upper count also includes changes that could fall on either side of a boundary. The same uncertain changes may appear in both ranges; do not add the upper counts.

    Windows use UTC dates, not launch times. Ranges cover only changes captured between saved snapshots; missed changes are not estimated. Nearby release windows can overlap.

    How the numbers are counted

    Upstream moved its summary statistics off the README and froze its own progress chart on October 6, 2026. Its problem data remains active. This independent view reads that data and checks the latest counts against the upstream summary on each refresh.

    “Resolved” combines proved, disproved, and otherwise solved. The seven remaining statuses, including ZFC independence, are grouped as unresolved; they are not stages on a path to a proof.

    A statement in Lean expresses the question in a formal language. A solution in Lean records a formal proof or disproof. Neither identifies who or what produced it; human review of the problem’s status can lag formalization.

    Model markers show selected public Claude releases and OpenAI API releases, not a complete release history. Their dates provide context; comparing windows does not establish that a model caused a change.

    We match problem numbers across the same snapshots as the Sankey. Repeated status changes are counted each time. Database additions and removals are counted separately.

    352 initially resolved + 177 changes to resolved + 54 added as already resolved − 6 changes back to unresolved − 1 removed from the database = 576 currently resolved. New database entries can describe old results.

    Daily averages count changes to existing problems. Each window starts at the last snapshot on or before its target start date. The count is divided by the actual days elapsed, shown below the chart.

    Monthly bars count changes in the month they first appear. The first and last months may be partial. All categories add up to the net change.

    Release comparisons use the 30 UTC dates before the release date and the 30 dates starting with it. An observed change is definitely inside a window only when its whole snapshot interval fits inside it. Intervals spanning a boundary contribute to a possible upper count, not a definite count. This includes snapshots on the boundary date because dates alone do not locate a change within that day. Exact rates require a complete window with no such uncertainty; a multiplier requires two such windows and a nonzero preceding count. These are bounds on captured changes, not all mathematical activity or all database edits.

    Gaps include days without updates and revisions skipped for invalid status data. Changes between snapshots may be missed or recorded later. Duplicate problem numbers cannot be matched reliably; their effect appears as “unmatched changes.”
